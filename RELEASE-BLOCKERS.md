# Release Blockers

What stands between this spike and a public Chrome Web Store release, grouped by severity. Each item states the risk — what breaks if it ships unfixed.

## Blockers — must fix before any public release

- [ ] **Trademark — nominative fair use, needs counsel review before public distribution.** The extension was renamed to "Bellhop" specifically to remove the vendor term from the product name: Palo Alto Networks publishes its own "Idira Identity Browser Extension" (600,000+ users, formerly "CyberArk Identity Browser Extension"), and CyberArk separately publishes a PVWA clipboard extension and a Secure Web Sessions extension — a name beginning "Idira" would sit confusingly beside a first-party extension. That resolves the primary risk, a vendor mark in the product name. What remains: "Idira" is still used descriptively in the extension's description and README (naming the marketplace it imports from), which is nominative fair use and carries a non-affiliation disclaimer — a materially weaker exposure than a mark in the name, but still worth a counsel pass before public distribution. It also automates the vendor's admin UI without vendor sanction, which is a separate, unresolved question. Distributing via GitHub rather than the Chrome Web Store (see "Distribution method undecided" below) reduces exposure somewhat — there is no store listing to pull and no store reviewer to flag it — but it does not eliminate either question. Strategic risk alongside it: if the vendor ships a native "Install" action, this extension becomes redundant.
- [ ] **SRS platform variant never tested.** The code routes `CPM|SRS → /Platforms/Import` and thereby claims support for both platform-import variants, but only the CPM variant has ever been exercised. CPM and SRS are both platform-import variants within the same Privilege Cloud service, not different vendors or products. Risk: shipping a claimed capability that may fail against real SRS data.
- [ ] **Non-super-admin users never tested.** Every verification run so far used maximum rights. Risk: the extension may fail, partially fail, or behave unpredictably for the majority of real users who are not super admins — untested against the platform's own permission model.
- [ ] **Chrome Web Store privacy policy and permission justifications — drafted, not finalised. Applies only if a Chrome Web Store route is chosen.** Conditional on the outcome of "Distribution method undecided" below: needed only if pursuing either a listed or an unlisted Web Store submission — an unlisted listing is still submitted for store review, so it still requires a privacy policy and permission justifications. Not needed at all if distribution goes the GitHub/self-hosted route. Drafts in `docs/PRIVACY.md` and `docs/STORE-PERMISSIONS.md`. If the store route is chosen, still needs: placeholders filled (publisher, contact, hosted URL, effective date), the policy hosted at a public URL, and legal review.
- [ ] **Distribution method undecided.** Chrome blocks installation of extensions not sourced from the Web Store, so this choice is load-bearing for everything else in this list — specifically, it determines whether `docs/STORE-PERMISSIONS.md` and the store privacy-policy blocker above are needed at all. Three viable routes, none yet chosen:
  - **(a) Load unpacked in developer mode.** Fine for internal/consultant use; the lowest-friction option. Risk: many enterprises disable developer mode via policy, which would block installation for exactly the admin users this extension targets.
  - **(b) Enterprise policy force-install from a self-hosted update URL.** Survives policy lockdown that blocks (a), and is likely the right fit for this audience (enterprise platform admins). Requires hosting an update manifest and signing a `.crx`, which is unbuilt.
  - **(c) Unlisted Chrome Web Store listing.** Installable by link only, no public discovery. Still goes through store review, and therefore still needs the privacy policy and permission justifications above — "unlisted" reduces discovery, not review burden.

## Should fix

- [ ] **Large artifacts vs. service worker idle lifetime.** Only a 308 KB artifact has been tested against the ~30s MV3 service worker idle timeout. Risk: a larger artifact's fetch + base64 encode gets killed mid-flight, failing imports for bigger components with no clear cause. Mitigation: an offscreen document.
- [ ] **Two tenants authenticated at once, never exercised live.** The CSRF cookie scope-ranking (`findXsrfCookie` in `src/csrf.ts`) was written specifically for this case but has never been run against two live authenticated tenants. Risk: the one scenario the ranking logic exists to handle is unverified in practice.
- [ ] **Raw HTTP response bodies rendered into the page DOM.** A duplicate import shows `HTTP 409 - {"ErrorCode":"CAWS00001E","ErrorMessage":"Creation of connection component PSM-SQLDeveloper failed. Reason: connection` — truncated mid-sentence. A 409 should read "Already imported into this tenant", with detail in the console. Risk: unsanitised, non-human-readable server output shown directly in the platform's UI.
- [ ] **No fetch timeouts.** Neither the S3 fetch nor the import POST has a timeout. Risk: a hung request leaves the button reading "Importing…" indefinitely, with no way for the user to know it failed or retry.
- [ ] **No CI.** Nothing runs `tsc` or `vitest` automatically; no ESLint/Prettier config exists despite being a stated project convention. Risk: a regression or type error ships unnoticed; style drifts with no enforcement.
- [ ] **No test coverage for `extension/content.js` or `extension/background.js`.** Only the pure `src/` modules are unit-tested; the DOM/network paths are validated manually only. Risk: the highest-risk, most-changed code paths have no regression safety net. (The origin-allowlist security check is being moved into `src/` with tests in a parallel task.)
- [ ] **Packaging does not exclude `recon/`.** `recon/` is a MAIN-world diagnostic observer that logs full request URLs, including presigned S3 URLs carrying live AWS credentials in the query string. Risk: shipping it in a store package leaks a live diagnostic/logging tool (and potentially credential-bearing URLs) to end users.
- [ ] **No extension icons; version is a static `0.1.0`.** No icon set, no versioning or release process. Risk: unpolished/rejected store listing, and no way to distinguish or roll back releases once published.

- [x] ~~"Already installed?" pre-flight check~~ — **decided: do not build.** The tenant-side lookups are good (`GET /PasswordVault/API/ConnectionComponents/{id}` returns the id or null; `GET /PasswordVault/API/Platforms/{PlatformID}` returns `PluginVersion`), but the marketplace payload carries only a marketplace-internal UUID and a display name, with no `PlatformID`/`ConnectionComponentID` and no relationship between the naming schemes. Matching would be fuzzy-on-name, and a false "already installed" would either block a legitimate import or misrepresent a production tenant. Versions are also on different axes (`latestVersion: "20"` vs `PluginVersion: "21.0.1"`). Revisit only if the marketplace API ever exposes a tenant-shaped identifier.

## Verified working

- Injection anchors on `data-testid="item-download"`, falling back to the `cyb-icon-download-*` icon class, then a structural anchor, then text. Residual risk: a vendor redeploy renaming both the test id and the icon class drops it to the fragile text match.
- Artifact origin is derived from the download URL at runtime and requested per-host; no vendor-internal bucket name is baked into the manifest.
- End-to-end import of a PSM connection component on a CPM tenant as super admin, including the confirmation dialog, per-tenant optional permission grant, and CSRF handling.
- Duplicate import is refused, not silently overwritten: `HTTP 409`, `ErrorCode CAWS00001E`. The existing failure path surfaces it, so no pre-flight check is required.
- 83 unit tests over the pure modules (`base64.ts`, `csrf.ts`, `tenant.ts`, `classify.ts`, `origins.ts`), including the origin allowlist that gates permission requests.
